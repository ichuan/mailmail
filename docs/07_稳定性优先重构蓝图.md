> 面向目标：**功能精简但极其稳定可靠**、**UI 简洁但不简陋**、**代码精炼可维护**、**测试充分可回归**、**安全默认开启**。

## 1. 执行摘要

当前项目已经具备可用基础：
- 前后端均有较完善测试基线；
- 已落地 IMAP IDLE 指数退避、SQLite WAL、SMTP 超时重试、HTML 净化等关键稳定性措施；
- 形成了“核心 + 插件”扩展架构，便于保持核心简洁。

但从“可用”走向“可靠”，仍有明显缺口：
1. **账号敏感信息仍在前端状态中明文驻留**（`password` 在 TS `Account` 类型和 Zustand 中存在）。
2. **数据库层仍保留 `accounts.password` 字段**，与“凭据仅在系统 Keychain 保存”的目标不完全一致。
3. **搜索、数据加载与状态管理仍偏内存驱动**，大邮箱场景下可预测性和性能风险仍在。
4. **测试覆盖虽多，但缺少统一质量门禁与分层覆盖目标**（契约测试、端到端与故障注入还不够系统化）。
5. **插件权限是声明式但非强隔离**，需要进一步做“能力收敛 + 默认拒绝 + 审计可追踪”。

建议采用“三阶段重构”：
- **Phase A（P0 稳定性与安全封口，2~4 周）**：先堵风险，不扩功能。
- **Phase B（P1 架构收敛，4~8 周）**：统一数据访问与状态模型，减少重复代码与隐性耦合。
- **Phase C（P2 体验增强，持续）**：做渐进披露 UI、可观测性与性能上限提升。

## 2. 现状调研（基于代码与文档）

### 2.1 已做得好的部分

- 项目目标明确：极简、隐私、本地优先。
- 文档已明确稳定性优先，且提供了当前风险列表（例如附件解析需更流式化）。
- 前端有插件框架（事件总线、槽位、权限），有助于把“复杂能力”隐藏在渐进层。
- Rust 层对 IMAP/SMTP/DB 已增加多项稳定性保护（超时、退避、WAL、容量边界）。

### 2.2 与目标不一致或高风险点

#### A. 凭据与隐私边界不够硬

- `src/store.ts` 中 `Account` 包含 `password` 字段，且账户数组常驻客户端 store。
- `src-tauri/src/db.rs` 的 `accounts` 表仍存储 `password`，插入/读取也携带该字段。

这意味着“即使有 keychain”，仍存在“明文副本”落盘与前端驻留风险，违背最小暴露原则。

#### B. 数据层仍是“前端内存为主”

- `store` 使用数组合并/去重/裁剪，已有内存上限策略，但搜索仍偏内存扫描（handover 文档也承认）。
- 这在多账户+历史邮件增长时会导致：首屏抖动、查询响应不稳定、逻辑分散（UI 与数据策略纠缠）。

#### C. 安全策略仍有提升空间

- HTML/CSS 追踪面防护已有（例如剥离 `<img>` 和 CSS `url()`），但缺少系统化策略矩阵：
  - 链接跳转策略（仅 `http/https` 已有，但还可做提示/域名告警）；
  - 附件处理策略（MIME 白名单、下载执行隔离、危险扩展名提示）；
  - 远程内容策略（每发件人信任白名单、一次性加载）。

#### D. 质量门禁与回归流程未“产品化”

- 当前有大量单测，但缺少**明确覆盖目标 + 分层测试策略 + 发布阻断标准**。
- 没有看到统一的“失败分类与处置时限”机制（crash、sync fail、数据损坏等）。

#### E. 代码复杂度与重复控制还可继续收敛

- 前端 store 承担了状态、事件、副作用、容量控制等多职责；
- 后端 IMAP 模块职责较重（协议、解析、净化、附件、状态上报），可拆分为更清晰边界。

## 3. 目标状态（Definition of Done）

### 3.1 产品层目标

1. **核心功能少而稳**：收信、读信、搜信、发信、账户管理、同步设置。
2. **复杂能力渐进披露**：默认隐藏高级项，通过设置页/上下文操作按需显现。
3. **弱网可用**：断网、超时、重连、账号异常均可恢复且有明确用户反馈。

### 3.2 工程层目标

1. **凭据零明文落盘**：DB 不存密码，前端不持久化密码。
2. **数据访问统一**：读取优先 DB 查询层，前端只做视图态缓存。
3. **测试门禁强制化**：PR 必须通过分层测试与关键指标阈值。
4. **安全默认开启**：远程内容默认禁用，链接/附件有防护提示链路。

## 4. 重构方案（可落地）

## 4.1 Phase A（P0）：稳定与安全封口（2~4 周）

### A1. 凭据模型重构（最高优先）

**改造目标**
- `Account` 分为：
  - `AccountPublic`（前端可见：id/name/email/server/port 等）
  - `AccountSecret`（仅后端短暂持有，用完即丢，来自 keychain）
- SQLite `accounts` 表去除 `password` 列（通过 schema v2 migration）。

**落地动作**
1. 新增 schema 版本升级：创建新表迁移数据、删除旧密码列（SQLite 通过重建表实现）。
2. `insert_account/get_accounts` 改为不读写密码。
3. Tauri command 改造：新增 `save_account_secret(accountId, secret)` 与 `resolve_account_secret(accountId)`（仅后端调用链使用，不暴露给插件）。
4. 前端 `store` 的 `Account` 类型移除 `password`。

**验收标准**
- 搜索全仓库不存在将密码写入 sqlite 的路径；
- 内存快照中无长驻密码字段；
- 历史用户升级后可无感迁移。

### A2. 同步与发送“可恢复性”增强

1. 为 IMAP/SMTP 失败定义**错误码体系**（认证失败/网络错误/协议错误/限流等）。
2. 将“重试策略”从代码散落常量提取为策略模块，可配置并可观察。
3. 添加“账号健康状态机”：`healthy/degraded/reconnecting/auth_failed/manual_action_required`。
4. UI 明确展示并给出下一步建议（重新登录、检查端口、稍后重试）。

### A3. 安全默认策略（读信场景）

1. 链接点击增加“外部域名提示 + 复制链接”双选项。
2. 附件下载增加 MIME 风险分级（可执行文件强提示）。
3. 远程图片策略细化：
   - 默认关闭；
   - 可“本邮件显示一次”；
   - 可“信任发件人后自动显示”。
4. 统一安全事件审计日志（不含敏感正文）。

### A4. 发布门禁落地

- 建立 `quality-gate` 脚本：`lint + typecheck + unit + integration + rust test + smoke e2e`。
- 关键路径失败（登录、收信、读信、发信、删除）一票否决发布。

---

## 4.2 Phase B（P1）：架构收敛与低重复实现（4~8 周）

### B1. 数据访问层（DAL）统一

目标：前端不再直接操作“全量邮件数组”为主，而是通过 query API（分页、过滤、排序、搜索）。

建议：
- Rust 提供 `query_emails(accountIds, folder, search, cursor, limit)`；
- 前端建立轻量 cache（按 query key 缓存页数据）；
- Zustand 只保存 UI 状态（当前查询条件、选中项、loading、error）。

收益：
- 代码更少（去掉大量手写 merge/prune 分支）；
- 行为更可预测；
- 大邮箱性能上限更高。

### B2. 模块职责拆分

- `imap.rs` 拆分为：
  - `imap_client`（连接与命令）
  - `mail_parser`（结构解析、编码处理）
  - `mail_sanitizer`（HTML/CSS 安全）
  - `sync_orchestrator`（同步流程/重试/事件上报）
- 每模块单测独立，降低回归范围。

### B3. 插件能力收敛

- 权限由“声明 + 运行时检查”升级为“最小能力 API 面”；
- 高风险能力（写邮件、读正文、网络访问）逐项弹性开关；
- 插件审计：记录插件调用高风险 API 的摘要事件。

---

## 4.3 Phase C（P2）：UI 与可观测性增强（持续）

### C1. 渐进披露式 UI

- 默认只显示：收件箱、搜索、写信、账户与同步。
- 高级功能（签名、打印、主题、通知、快捷键）收纳于“高级设置”与上下文菜单。
- 统一“空状态/错误状态/加载状态”设计语言，保持“简洁但不简陋”。

### C2. 可靠性可观测

- 定义核心 SLI：
  - 首屏可交互时间；
  - 同步成功率；
  - 发信成功率；
  - 平均恢复时间（MTTR）。
- 离线日志包导出（脱敏）支持用户反馈与诊断。

---

## 5. 测试策略（覆盖每个小功能 + 整体）

### 5.1 分层策略

1. **单元测试**：纯逻辑（解析、去重、权限判断、重试策略）。
2. **契约测试**：前后端 IPC command payload 与错误码一致性。
3. **集成测试**：SQLite + IMAP mock + SMTP mock 的端到端流程。
4. **E2E 冒烟**：添加账号→同步→阅读→回复→删除。
5. **故障注入测试**：断网、超时、证书错误、权限拒绝、数据库锁竞争。

### 5.2 覆盖目标（建议）

- Rust 核心模块行覆盖：≥ 80%；关键分支覆盖：≥ 90%。
- 前端核心状态与关键组件：行覆盖 ≥ 75%，关键流程分支 ≥ 90%。
- 每次发布前必须跑完整 quality-gate。

### 5.3 安全测试专项

- XSS payload 回归集（HTML、SVG、CSS url、data URI、畸形 MIME）。
- 恶意附件样本（脚本、双扩展名、伪装 MIME）。
- 链接诱导测试（同形异义域名、短链重定向）。

---

## 6. 安全基线（补充建议）

1. **最小日志原则**：日志默认不输出邮箱地址全文，改哈希或掩码。
2. **内容隔离**：邮件正文渲染容器启用更严格 CSP（若 Tauri/WebView 能力允许，尽量禁内联脚本）。
3. **协议白名单**：仅允许 `https/http/mailto`（若支持），明确拒绝 `file://` 等危险协议。
4. **依赖治理**：建立前后端依赖漏洞扫描（npm audit/cargo audit）并设阈值。
5. **供应链策略**：插件源签名与校验（未来如支持第三方插件市场）。

## 7. 实施计划（建议节奏）

### 7.1 里程碑

- **M1（第 2 周）**：密码移除落盘 + 前端类型清理 + 基础迁移完成。
- **M2（第 4 周）**：错误码体系 + 状态机 + UI 错误反馈联动。
- **M3（第 8 周）**：DAL 查询化 + store 收敛 + 关键流程 E2E 稳定。
- **M4（持续）**：渐进披露 UI 与可观测平台完善。

### 7.2 风险与回滚

- DB 迁移前必须自动备份；
- 每个里程碑保留 feature flag；
- 如果出现严重回归，可切回旧路径（只读模式 + 禁止 destructive 操作）。

---

## 8. 你可能还没提到、但建议纳入的要求

1. **可维护性预算**：每个新增功能必须定义“可删性”（不满意可快速移除，不污染核心）。
2. **性能预算**：定义单账号 1 万封邮件场景下的查询与渲染目标。
3. **可访问性（a11y）**：键盘全流程可达，阅读器可读。
4. **可国际化一致性**：所有新文案强制走 i18n key，避免中英文硬编码漂移。
5. **升级兼容策略**：跨版本 schema、插件 API 版本协商与弃用窗口。

## 10. 结论

这个项目离“好用”已经不远，下一步关键不是“加功能”，而是**把稳定性、安全性、可维护性做成默认能力**。建议先完成 P0 封口，再推进 P1 架构收敛；这样能在不牺牲“极简体验”的前提下，把可靠性和长期迭代效率显著抬升。
